## Core Decision/Topic

Mount the Space Lens workbench inside the DeepSeek Harness as a plugin
(`dsh-plugin-spacelens`), following the architecture of Refyard's
`feat(integrations): add the DeepSeek Harness plugin` (41d44e7): never reimplement
the product — start a real Space Lens server inside the Harness host process and
frame its own SPA behind a Harness web route. Plus a follow-up desktop/web header
fix: the ready-state header drew a lucide `Search` icon instead of the real logo,
and its traffic-light padding was macOS-only.

## Options Considered

**How "scan the open project's folder" reaches the engine:**

1. *Loosen `ScanManager.containRoot` / hot-swap roots* — rejected outright. The
   per-server scan roots ARE the product's security model; a plugin reaching into
   them would weaken the standalone CLI with the same code.
2. *Spawn `spacelens serve` as a subprocess* — rejected. Process supervision,
   readiness parsing and teardown for what one in-process call does; the plugin
   would also drag the napi engine resolution through a second package layout.
3. **One `startServe` per requested directory (chosen)** — roots are fixed at
   startup by design, so "which folder is open" becomes "which server answers
   this frame": one loopback, port-0 listener per project, never restarted,
   torn down with the plugin. Read-only (`allowCleanup: false`): a panel a
   session opened implicitly must never make trashing the easy path.

**How a frame's API calls find their server:** the SPA composes every call from
the `?api=` base alone and carries no query, so the directory must travel inside
the base — `/space-lens/d/<encoded dir>`, a segment belonging to the plugin; the
upstream never sees it. This bug was found by testing (exchange answered 404
"no directory known" before the fix), not by reading.

**Embedding surface:** add an `embed` build flavor to `apps/web`
(`SPACLENS_EMBED_BASE` → `kit.paths.base`, service worker off) rather than patch
served bytes — base-path URLs and the missing service worker registration are
baked into the document, so they must be a build. Similarly `createAssetHandler`
gained a `frameAncestors` option (default `'none'` unchanged) instead of the
plugin rewriting CSP headers mid-proxy.

## Key Changes Made

- `integrations/dsh/` — new bundle: `src/host.ts` (route, per-directory servers,
  pairing redirect, proxy, Host/Origin gate), `src/client.ts` (sidebar entry,
  main panel, right-column tab, header button), manifest, icon, locale, README.
- `scripts/build-dsh-plugin.mjs` + root `build:dsh` — embed SPA, host bundle
  (write-only-when-changed; the Harness remembers a bad bundle read for the
  process lifetime), and the napi engine staged at `dist/node_modules/space-lens`
  so the scan worker's `createRequire(import.meta.url)` resolves it inside the
  bundle. The engine is the one package that must NOT be bundled (platform
  `.node` loading).
- `packages/host`: `frameAncestors` threaded `ServeOptions → config → assets`,
  CSP cache key extended with the frame-ancestors value (a real bug the new
  regression test caught: two handlers over one web root shared the first
  policy), regression test added — host suite 43/43.
- `apps/web`: embed flavor in `svelte.config.js`; header logo swapped from the
  `Search` icon to `logo-mark.png`; `headerInset()` replaces the hardcoded
  `pl-[140px]` — browser `px-4`, macOS `pl-[88px]` (traffic lights ≈78px),
  Windows `pr-[152px]` (three caption buttons, right side), detected via
  user agent to avoid a Tauri OS plugin for one padding decision.
