# 2026-10-22 19:20

## Core Decision/Topic

The desktop shell could not scan the startup disk: the drive list showed
"Macintosh HD" as **outside scan roots** with no Scan button, and typing `/`
by hand was refused with `Forbidden: path is outside the roots this desktop
session serves`. The HTTP host could scan it all along.

## Options Considered

**Why the desktop could not scan `/`:**
- *The engine refuses it* — true, but the engine only refuses what the
  **session roots** do not cover. The refusal was the symptom, not the cause.
- *The roots are wrong* — **the cause**. `default_roots()` in
  `apps/desktop/src-tauri/src/lib.rs` served `$HOME` and `/Volumes`. The
  2026-10-04 commit `a5d0844` added `/Volumes` so external drives became
  scannable, and the startup disk was never added.
- *The product does not support whole-disk scans* — false. The protected
  scanner (`localOnly: true`), the `macos-no-materialization` coverage
  contract, the `Macintosh HD` label, `scanTargetPaths()`'s
  `['/', '/System/Volumes/Data']` pair, the `FULL_DISK_PATHS` gate and
  `FULL_DISK_SCAN_REPORT.md` are all whole-disk machinery. The desktop simply
  never got the roots that let it in.

**Which roots to add:**
- *`/` only* — the drive list's scannable test would pass, but `scanTargetPaths`
  pairs `/` with `/System/Volumes/Data` whenever the host offers Data, and the
  protected walker is built to treat the Data volume as its own root (nested
  roots are excluded from the parent traversal, so the disk is counted once).
- **`/` and `/System/Volumes/Data` together (chosen)** — the same pair the
  browser host uses with `--root /`, and the pair the measured
  `FULL_DISK_SCAN_REPORT` run used.

**Is serving `/` a security regression?**
- The per-session roots are the product's security model (journal
  2026-09-24-1656), and the HTTP host keeps that model by making the root an
  *operator* decision (`--root /`).
- The desktop is a local, single-user GUI with no remote clients, and its
  scanner is the protected one: cloud paths are excluded before metadata, iCloud
  is never downloaded, and the startup-disk scan has been measured end to end
  on this exact machine. Serving `/` gives the desktop the same reach the
  browser host already has by explicit configuration.
- Cleanup stays guarded: the configured roots themselves can never be cleaned
  (`guard_cleanup_roots`), and the whole-disk scan is read-only by default.

## Key Changes Made

- `apps/desktop/src-tauri/src/lib.rs` — `default_roots()` now serves `/` and
  `/System/Volumes/Data` on macOS alongside `$HOME` and `/Volumes`; the
  macOS roots test asserts the startup disk is served.
- Nothing else changed: the engine, the protected scanner and the frontend
  already spoke this shape (the frontend always sends `localOnly: true`, and
  `scanTargetPaths` already paired the two roots).

## Verification

Desktop shell built and launched on the machine: the drive list now offers
**Scan** on Macintosh HD, the sidebar lists "Macintosh HD" and "Data", and a
whole-disk scan completed — 6,390,178 items · 265 GiB · 6.39M entries, treemap
and folder contents populated, "161,375 skipped" coverage reported and the
breadcrumb's new "Reveal / in the file manager" button present.

Also observed: a **debug** build scans the whole disk far slower than the
release build the `FULL_DISK_SCAN_REPORT` measured (12.7 s of Rust traversal).
Whole-disk runs should use a release build.

## Future Considerations

- The desktop roots are now `$HOME`, `/`, `/System/Volumes/Data` and
  `/Volumes`; `/` already contains `/Volumes`, so the two entries are
  redundant on macOS. Harmless today (the roots are a containment list, not a
  traversal list), but a nested-root dedupe would be tidier.
- Linux and Windows keep their mount/drive-letter roots; the startup disk on
  Linux (`/`) and on Windows (`C:\`) are still not served, and the same
  argument as macOS applies to them.
- The VS Code webview still has no host request for the file-manager reveal.
