## Core Decision/Topic

A scanned folder could not be opened in the OS file manager from anywhere in the
product: the Folder contents context menu offered "Add to review selection" and
"Open <name>" (which only navigates *inside* Space Lens), and the app-location
"Reveal in Finder" button was scoped to audited app locations only. The request
was a context-menu entry that shows the item in the host's file manager —
"Reveal in Finder" on macOS, "Reveal in Explorer" elsewhere — working from both
the web workbench and the desktop shell.

Follow-up in the same session: the action became **two** (reveal *and* open),
and it was added to the discovery views and the breadcrumb as well.

## Options Considered

**Where the file manager is opened:**
- *The browser* — a web page cannot open a local folder; the browser has no
  path at all. Dead end.
- **The host, always (chosen)** — the web workbench asks the host that ran the
  scan to open the folder, so the browser case and the desktop case are the
  same request. The desktop shell answers it over Tauri IPC; `spacelens serve`
  answers it over HTTP.

**Which path may be opened:**
- *Whatever the client asks for* — a remote client could name any path on the
  server's disk (`/etc/passwd`) and have the server open it in its own Finder.
- **Containment in the roots the host serves (chosen)** — the host resolves the
  path against the roots it already serves for scans (`config.roots` for HTTP,
  the shell's home + mount roots for the desktop) and refuses anything else
  with `Forbidden` before a process is spawned. The scan tree can only contain
  paths under those roots, so nothing legitimate is lost.

**Label ("Reveal in …" vs "Open in …"):**
- *One hard-coded label* — wrong on two of three platforms, and the web case
  runs on the *server's* OS, not the browser's.
- **The host announces its platform (chosen)** — `capabilities.host.platform`
  (macOS / windows / linux / unknown) lets the UI say "Reveal in Finder",
  "Reveal in Explorer" or "Reveal in File Manager" for the machine that
  actually holds the folder.

**One action or two:**
- *One* ("open the folder") — a folder shows its contents but its place in the
  filesystem is lost; the parent is never visible.
- *One* ("reveal in the parent") — the item is highlighted in its parent, but
  the user still cannot dive into the folder itself.
- **Both (chosen)** — `reveal` shows the item in its parent folder, selected
  (`open -R`, `explorer /select,`; Linux opens the parent, it cannot select a
  row); `open` opens a folder in the file manager itself (`open <dir>`,
  `explorer <dir>`, `xdg-open <dir>`). `open` is **folders only**: opening a
  *file* would launch it, and a disk tool must never do that by accident — the
  host answers `InvalidRequest` for a file.

**Folder vs file semantics:** settled by the two actions above: a file can be
revealed but never opened; a folder can be both.

## Key Changes Made

- `packages/contract` — new `src/reveal.ts` (`RevealPathRequestSchema` with the
  optional `action` (`reveal` | `open`), `RevealPathResultSchema`); the
  `host:reveal` scope; `capabilities.host` gains optional `pathReveal` and
  `platform`; regenerated `generated/contract.schema.json`.
- `packages/host` — new `src/reveal.ts`: containment against the served roots
  (component-aware, so `/a/bc` is not inside `/a/b`), `lstat` existence check
  (a symlink is revealed as the link the scan reported, never resolved to its
  target), and the per-platform launcher for both actions. New route
  `POST /api/v1/host/reveal` behind the `host:reveal` scope; the launcher is
  injectable so tests never open a real window.
- `packages/client` — `WorkbenchService.revealPath?`; HTTP adapter posts to
  `/api/v1/host/reveal`; Tauri adapter sends the `revealScanPath` host-request
  arm (a separate arm from the app-location `revealPath`).
- `apps/desktop/src-tauri` — new `src/reveal.rs` (containment, existence,
  platform launcher, `RevealAction` enum, cfg(test) hook instead of a real
  spawn); `HostRequest::RevealScanPath` carries the optional action;
  capabilities declare `pathReveal` + `platform`.
- `packages/web-ui` — new `lib/file-manager.ts` (`fileManagerLabel(platform,
  action)`); the `ChildList` context menu gained both entries (the open one
  only for folders), disabled for skipped rows, accounting leaves and
  synthetic app paths; `DiscoveryList` rows gained a reveal button; the
  `BreadcrumbBar` gained a reveal button for the current folder.
- `apps/web` — `pathRevealAvailable` gate (capability *and* method, like every
  other gate), one page handler for both actions, wiring for all three
  surfaces.

## Verification

svelte-check (web, web-ui) and contract/host/client typechecks clean; contract,
host (186), client, web-ui and web test suites pass; the desktop Rust suite
passes (67 tests, including the reveal tests), `cargo fmt` + `clippy` clean.
Live against `spacelens serve --dev-open-session`: capabilities report
`pathReveal: true, platform: "macos"`; a served folder reveals (parent window,
item highlighted) and opens (the folder itself), a served file reveals but is
refused for `open` with `InvalidRequest`, a path outside the roots is refused
with `Forbidden`, a missing path answers `NotFound`. Not verified: the desktop
shell end to end (needs a full bundle build) and the Windows/Linux launchers
(no such machine here).

## Future Considerations

- The VS Code webview uses the same `ChildList` but has no host request for
  this yet; it would need a `vscode.env.openExternal` command arm.
- The HTTP host opens a window on the *server's* desktop. For a shared host
  that is a visible side effect of a remote click — the `host:reveal` scope
  exists so it can be withheld, but the operator flag for it does not yet.
- `capabilities.host.platform` is host-wide; a per-request platform would be
  needed if a host ever served several filesystems.
