# 2026-09-24 17:45

## Core Decision/Topic

Release channel for `dsh-plugin-spacelens`: npm public (user's choice over a
GitHub-release tarball or staying local-only). The plugin was previously
local-only — a profile symlink into the working tree, `"private": true`, name
unclaimed on the registry.

The deciding fact is one refyard did not have: the `space-lens` engine itself
is published on npm (0.2.8, per-platform optionalDependencies). So the plugin
package never ships a binary — it declares `"space-lens": "^0.2.8"` and every
installing machine pulls its own native engine, which is exactly why npm beats
a release tarball here.

## Options Considered

- **GitHub release tarball** — install means downloading by hand; no dependency
  resolution, so it would have to ship a darwin-arm64 binary and lie about
  portability.
- **Stay local-only** (refyard's choice) — fine for one machine, but the engine
  condition makes publishing nearly free, so the tradeoff flipped.
- **npm public (chosen)** — `plugin_manager install_bundle dsh-plugin-spacelens`
  from any profile; versioned; platform-correct.

## Key Changes Made

- `integrations/dsh/package.json` — not private; depends on npm `space-lens`;
  repository/keywords; `prepublishOnly` builds through the repo's `build:dsh`.
- `scripts/build-dsh-plugin.mjs` — the staged engine moves from
  `dist/node_modules/` to the package root's `node_modules/`. Reason discovered
  by packing: `files: ["dist"]` drags a nested `dist/node_modules` into the
  tarball and neither `files` trimming nor `.npmignore` could exclude it, while
  npm excludes a package's own root `node_modules` unconditionally. Resolution
  is unchanged — Node walks up from `dist/host.js` either way (verified against
  both a flat and a sibling-dep layout).
- `.github/workflows/dsh-plugin.yml` — tag `plugin-v*` gates and publishes
  (`npm publish --access public` with `NPM_TOKEN`; the tag version must equal
  `package.json`'s). PR-path triggers keep the bundle compiling.
- README: install (npm name vs. repo path), release, and the never-pack-the-
  engine rule.

## Verification

`npm pack --dry-run`: 41 files, zero `node_modules` entries, 1.6 MB; engine
resolves from the new location; svelte/type gates unaffected. Actual publish
not run — it needs the user's `NPM_TOKEN` secret (CI route) or npm login
(local route; the machine's `~/.npm` cache also needs `sudo chown` first, an
old root-owned-files bug).

## Future Considerations

- First publish doubles as the name claim on the registry; after that, the
  Harness can install the plugin by bare name anywhere.
- The updater story differs from the desktop app: bundles re-read on Harness
  restart, so plugin upgrades are version-bump + reinstall, no auto-update.
